# Aegis Engine: AOI (Area of Interest) 空间索引模块

## 1. 模块简介 (Overview)

`AOIGrid` 是 Aegis 引擎中专为高频实体交互场景（如 MMORPG、百人竞技）设计的**高性能 2D 空间索引容器**。

### 1.1 核心解决的问题：广播风暴 (Broadcast Storm)

在多人同屏场景中，如果采用全局广播，N 个玩家的单次移动会导致 $O(N^2)$ 的消息量（例如 2000 人同屏将瞬间压垮服务器）。

AOI 模块通过空间划分，只将实体的状态变化通知给其“视野范围内”的其他实体，成功将消息复杂度从 $O(N^2)$ 降维至 $O(N \times M)$（$M$ 为视野内平均人数，通常 $< 50$），实现了服务器承载能力的线性扩展。

### 1.2 模块特征

- **极速：** 核心增删改查操作均为严格的 $O(1)$ 时间复杂度。
    
- **Actor 模式深度优化：** 针对 Actor 模型设计的**天然无锁化**实现，完全消除原子操作与锁竞争开销。
    
- **DOD (面向数据设计)：** 极致的 Cache 局部性优化，全程零内存碎片。
    

## 2. 核心架构设计 (Architecture)

本模块采用**固定网格 (Fixed Grid)** 方案，而非四叉树 (QuadTree)。以牺牲部分空闲区域的内存为代价，换取了极致的 CPU 寻址速度。

### 2.1 AOICell (空间单元)

网格的最基本组成部分，采用极简的 POD 风格。

```
struct AOICell {
    std::vector<EntityId> entities;       // 实体列表
};
```

- **零内存碎片：** 抛弃传统的十字链表（Linked List），采用连续内存的 `std::vector`。
    
- $O(1)$ **删除：** 采用 **Swap-and-Pop** 惯用法，移除实体时将队尾元素覆盖至待删位置并 `pop_back`，规避了 `erase` 带来的 $O(N)$ 数据平移开销。
    

### 2.2 AOIGrid (网格管理器)

采用打平的一维数组 `std::vector<AOICell> cells_` 模拟二维地图。

- **扁平化内存：** 杜绝了 `vector<vector<...>>` 带来的指针跳跃，极大提高了 CPU L1/L2 Cache 的命中率。
    
- **零分配 (Zero-Allocation)：** 在 `init_internal()` 时一次性 `resize` 预分配所有网格内存。运行时杜绝任何 `malloc/new`，彻底根除性能抖动。
    

## 3. 极致性能优化 (Technical Highlights)

为了压榨 CPU 的最后一滴性能，本模块在指令级和算法级进行了深度优化：

### 3.1 视野 Diff 的“降维打击”算法

当实体跨越格子时（`Move` 操作），需要计算“谁新进入了视野”与“谁离开了视野”。
    
- **网格索引差集：** 提取新、旧九宫格的网格索引（恒定最多 9 个整数），利用 `std::ranges::set_difference` 进行差集运算。
    
- **收益：** 视野计算复杂度彻底与场景拥挤度解耦。无论格子里有 10 人还是 1000 人，Diff 开销永远是微秒级的常数时间。

- **重用缓冲区：** 内部使用 `thread_local` 容器缓存差集结果，消除了频繁移动产生的临时内存分配。
    

### 3.2 浮点数与分支预测优化

- **除法变乘法：** 预缓存 `invCellSize_ = 1.0f / cellSize_`，在热点路径（坐标转索引）中用乘法（1~3 CPU Cycles）替代除法（10~20 Cycles）。
    
- **趋零截断：** 利用 `static_cast<uint32_t>` 对正浮点数的天然截断特性，省去 `std::floor` 函数调用。
    
- **消除循环分支：** 在九宫格遍历器 `ForEachNeighborIndex` 中，预先在循环外计算好安全的 `[startRow, endRow]` 边界，使得内层循环成为纯粹的线性累加，完全避免了 CPU 分支预测失败（Branch Misprediction）的流水线清空惩罚。
    

### 3.3 浮点数黑洞与安全防御

通过 `std::clamp` 将坐标硬性锁定在非负安全区间，从底层拦截了物理引擎抖动可能产生的极小负数（如 `-1e-7`），彻底杜绝其强转为无符号整数后引发的整数下溢环绕（Integer Underflow）和内存越界崩溃。

## 4. 并发控制模型 (Concurrency)

本模块深度适配 **Actor 模型**（如 Skynet/Orleans 模式）。

- **单线程保证：** 每个 `AOIGrid` 实例归属于特定的地图 Actor，其内部状态的所有变更（Add/Move/Remove）由 Actor 保证在单一线程序列执行。
    
- **消除自旋锁：** 摒弃了传统的自旋锁（SpinLock），消除了 `lock` 指令带来的 **Cache Line 争用**（False Sharing）和原子操作开销。
    

## 5. 工程实践与选型 Q&A (Trade-offs)

**Q：为什么选用固定网格，而不是四叉树 (QuadTree) 或十字链表？**

> **A：** 四叉树适合极其稀疏且边界庞大的大世界，其树节点的指针跳转（Cache Miss）和树平衡维护成本在人员密集的 MMO 场景下极其昂贵。十字链表同理，内存不连续导致遍历性能极差。网格虽然在没人去的死角会浪费少量内存，但换取了物理内存的绝对连续性和纯数组索引的 $O(1)$ 速度，在密集战斗场景下是唯一解。

**Q：格子大小 (`cellSize`) 应该如何设定？**

> **A：** 经验值为 **实体视野半径的 1/2 到 1 倍**。
> 
> - **若太小：** 九宫格不足以覆盖视野，需要向外扩展至 25 宫格甚至 49 宫格，导致寻址遍历开销激增。
>     
> - **若太大：** 九宫格会框入大量实际上处于视野边缘之外的无关实体，导致带宽严重浪费（客户端收到包后也会裁剪抛弃）。
>
